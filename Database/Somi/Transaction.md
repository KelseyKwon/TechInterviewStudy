# 트랜잭션 ( Transaction )

> **데이터베이스의 상태를 변화시키기 위해 수행되는 작업들의 논리적 단위**
> 
- 여러 개의 DML 작업(SELECT/INSERT/UPDATE/DELETE)이 묶여 하나의 완전한 작업 단위
- 사용자가 시스템에 대한 서비스 요구 시 시스템이 응답하기 위한 상태 변환 과정의 작업단위
    - 이러한 트랜잭션은 상황에 따라 저장 혹은 철회 될 수있음
        
        → 모든 작업이 완전히 수행되거나 전혀 수행되지 않아야 DB의 일관성이 유지
        
    
    <aside>
    
    - **커밋(Commit)**: 모든 부분작업이 정상적으로 완료하면 이 변경사항을 한꺼번에 DB에 반영한다.
    - **롤백(Rollback)**: 부분 작업이 실패하면 트랜잭션 실행 전으로 되돌린다.
    </aside>

### 스프링부트 EX ) 체스 미션

> 
> 
> 
> **비즈니스 로직 :**
> 
> a2 포지션의 폰을 a4 포지션으로 옮기려면 
> 
> a2 포지션은 blank로, a4 포지션은 pawn으로 변경해야함
> 

**💣 문제 상황 :** 

만약 위 로직이 다른 트랜잭션에서 작동하다 a2 포지션을 blank로 바꾼 후, a4 포지션을 옮기기 전, 에러가 발생한다면

1. a2 → blank 로 업데이트 성공
2. a4 → pawn 으로 업데이트 하려는 순간 에러 발생

**a2 = blank , a4 = blank → pawn이 사라짐 ( 데이터 무결성( = 논리적 일관성 ) 위배 )**

⁉️ 왜 이런 일이 생기냐 :  두 쿼리가 각각 다른 트랜잭션으로 실행되었기 때문

✅  **이 비즈니스 로직은 반드시 전부 성공하거나 전부 실패해야함 !**

**하나라도 실패할 시 Rollback ( 철회 )해야함**

이러한 문제를 해결하기 위해 주로 비즈니스 로직이 존재하는 **Service 레이어**에서 트랜잭션을 관리

```java
@Service
@Transactional
public void movePawn() {
    updateA2();
    updateA4();
}
```

## 트랜잭션 핵심 특징 : ACID

### **1.원자성 (Atomicity)**

- All or Nothing
- 트랜잭션의 작업이 부분적으로 실행되거나 중단되지 않는 것을 보장
- **save point**
    - 일반적으로 Rollback을 명시하면 INSERT, DELETE, UPDATE 등의 작업 전체가 취소
    - SAVEPOINT를 사용하면 전체가 아닌 특정 부분에서 트랜잭션을 취소
    - 취소하려는 지점을 SAVEPOINT로 명시 후 `ROLLBACK TO SAVEPOINTNAME;`

### 2.일**관성 (Consistency)**

- 트랜잭션 전후로 **데이터베이스의 제약조건 등이 항상 유지**
- **트리거(Trigger)**
    - NSERT, DELETE, UPDATE 같은 DML 문이 수행되었을 때, 데이터베이스에서 자동으로 동작
        
        → 사용자가 직접 호출하는 형태가 아니라, 데이터베이스에서 자동적으로 호출
        
    - 한쪽 데이터베이스의 테이블에 정보의 수정이 일어났을 경우 다른 쪽 테이블에도 함께 정보가 수정될 수 있도록 자동 업데이트를 하는 명령 등을 구성

### **3.격리성 (Isolation)**

- 여러 트랜잭션이 동시에 수행될 때 서로 영향을 주지 않아야 함
- **Lock & Unlock**
    - 데이터 작업 중일 때는 해당 영역 Lock : 다른 트랜잭션이 접근하지 못함
    - 트랜잭션의 요청이 끝나면 Unlock : 다른 트랜잭션이 처리될 수 있도록 허용
    - 잘못 사용하면 어떠한 트랜잭션도 수행될 수 없는 **데드락(Deadlock)** 상태 발생
    
    ### ⁉️ . 갱신 분실 문제 ( Lost Update )
    
    > 
    > 
    > 
    > 두 개 이상의 트랜잭션이 동시에 같은 데이터를 수정할 때 
    > 
    > 한 트랜잭션의 수정 결과가 다른 트랜잭션에 의해 덮어써져 사라지는 현상
    > 
    
    ```java
    초기 값: 잔액 = 100
    - T1: 100 → 200으로 수정
    - T2: 100 → 300으로 수정
    결과: 300 -> T1의 갱신이 사라짐
    ```
    
    - 트랜잭션이 서로의 수정 사실을 모른 채 동시에 동일한 데이터를 읽고 수정했기 때문에 발생
    
    ### ✅ . Locking
    
    - **Shared Lock (S Lock)**
        - 읽기 허용, 쓰기는 불가
    - **Exclusive Lock (X Lock)**
        - 읽기/쓰기 모두 독점, 다른 트랜잭션 접근 불가
    
    →  락이 많아질수록 성능 저하
    → 잘못 설계 시 **데드락(Deadlock)** 상태 발생
    
    ### ✅ 2. MVCC ( 다중 버전 동시성 제어 )
    
    > 데이터를 여러 버전으로 관리하여 읽기와 쓰기를 충돌 없이 동시에 처리
    > 
    - 읽기 트랜잭션은 → 자신이 시작한 시점의 스냅샷을 읽음
    - 쓰기 트랜잭션은 → 새로운 버전 생성

### **4.지속성 (Durability)**

- 성공적으로 수행된 트랜잭션의 결과는 영구적으로 저장
- 트랜잭션이 성공적으로 종료되어 Commit 후, 해당 데이터는 데이터베이스에 영원히 반영

## 트랜잭션 격리수준

> 
> 
> 
> 여러 트랜잭션이 동시에 처리될 때, 
> 
> 특정 트랜잭션이 다른 트랜잭션에서 변경하거나 조회하는 데이터를 볼 수 있게 허용할지 여부를 결정
> 
- **SERIALIZABLE**
    - 가장 강한 격리 수준
    - 모든 트랜잭션이 순차 실행된 것처럼 동작
    - 트랜잭션이 순차적으로 처리되어야 하므로 동시 처리 성능이 매우 떨어짐
- **REPEATABLE READ**
    - 한 트랜잭션 안에서는 같은 데이터를 여러 번 읽어도 동일한 결과
    - MVCC를 이용해 한 트랜잭션 내에서 동일한 결과를 보장
- **READ COMMITTED**
    - 커밋된 데이터만 읽기 가능
- **READ UNCOMMITED**
    - 다른 트랜잭션의 커밋되지 않은 데이터 읽기 가능

- Dirty Read : 커밋되지 않은 데이터를 다른 트랜잭션이 읽는 것
- Non-Repeatable Read :  같은 트랜잭션 안에서 같은 데이터를 두 번 읽었는데 값이 달라지는 현상
- Phantom Read : 같은 조건으로 조회했는데, 조회 결과 행의 개수가 달라지는 현상

## 조인 ( Join )

> 두 개 이상의 테이블을 연결하여 하나의 결과 집합을 생성하는 연산
> 
- **INNER JOIN**
    - 두 테이블의 교집합만 조회
    - 매칭되는 데이터만 반환
- **LEFT JOIN**
    - 왼쪽 테이블 기준
    - 오른쪽 테이블에 값이 없으면 NULL
- **RIGHT JOIN**
    - 오른쪽 테이블 기준
- **OUTER JOIN**
    - 양쪽 테이블 모두 포함 (매칭 안 되면 NULL)

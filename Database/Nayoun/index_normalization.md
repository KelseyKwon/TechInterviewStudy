# DDL / DML / DCL

## DDL

> 데이터 정의어
> 
- `create` : 데이터베이스, 테이블등을 생성
- `alter` : 테이블을 수정
- `drop` : 데이터베이스, 테이블을 삭제
- `truncate` : 테이블을 초기화

***SCHEMA, DOMAIN, TABLE, VIEW, INDEX를 정의하거나 변경 또는 삭제할 때 사용하는 언어***

***데이터 베이스 관리자나 데이터베이스 설계자가 사용***

## DML

> 데이터 조작어 → DB에 입력된 레코드를 조회하거나 수정 or 삭제한다.
> 
- `select` : 데이터 조회
- `insert` : 데이터 삽입
- `update` : 데이터 수정
- `delete` : 데이터 삭제

***데이터베이스 사용자가 응용 프로그램이나 질의어를 통하여 저장된 데이터를 실질적으로 처리하는데 사용하는 언어***

***데이터베이스 사용자와 데이터베이스 관리 시스템 간의 인터페이스를 제공***

## DCL

> 데이터베이스에 접근하거나 객체에 권한을 주는 등의 역할을 하는 언어
> 
- `grant` : 특정 데이터베이스 사용자에게 특정 작업에 대한 수행 권한을 부여
- `revoke` : 특정 데이터베이스 사용자에게 특정 작업에 대한 수행 권한을 **박탈, 회수**
- `commit` : 트랜잭션의 작업을 저장
- `rollback` : 트랜잭션의 작업을 **취소, 원래대로 복구**

<aside>
💡

**ROLE의 종류**

`CONNECT` : DB 접속 권한

`RESOURCE` : 테이블이라든지 인덱스라든지 생성할 수 있는 권한

`CREATE VIEW` : 뷰 생성 권한

`DBA` : 모든 권한(관리자)

</aside>

# Index

> 추가적인 쓰기 작업 & 저장 공간을 활용해, DB 테이블에 저장된 데이터의 검색 속도를 향상시킨다.
> 

**HOW?**

<img width="545" height="321" alt="스크린샷 2026-02-20 오전 11 05 28" src="https://github.com/user-attachments/assets/b74fc2b0-dc59-443f-9a97-6b11c8865d53" />

→ 특정 column or column의 조합에 대한 값 + 해당 값이 저장된 레코드의 위치를 매핑

- 장점
    - 검색 대상 레코드의 범위를 줄인다. (검색 속도 향상)
    - 중복 데이터 방지, 특정 컬럼의 `Unique`을 보장할 수 있다.
    - `ORDER BY`, `GROUP BY`, `WHERE` 등이 사용되는 작업이 더욱 효율적으로 처리됨!
- 단점
    - 인덱스를 위한 추가적인 저장 공간이 필요
    - `CREATE`, `DELETE`, `UPDATE`시에도 인덱스를 업데이트 해야 함 → 성능 저하 발생!
    - 한 페이지를 동시에 수정할 수 있는 병행성이 줄어듦.
    - 인덱스 생성 시간이 오래 걸릴 수 있다.

- 즉, 테이블의 물리적인 데이터 저장 순서를 `index key` 순서와 일치시킨다.
- `Dictionary` 방식 (like 국어 사전)
- 테이블 당 단 하나만 생성 가능!
    - 왜? 데이터 자체가 물리적으로 정렬되어 있기 때문에

<aside>
💡

*⇒ 테이블 당 하나만 생성 가능한 것의 보충 설명*

기본적으로 `PK`를 `Clustering Key`로 선택한다.

하지만 `PK`가 없다면? `NOT NULL` 옵션의 `Unique Index`중 첫 번째 인덱스를 `clustering key`로 선택.

이것도 없다면? 내부적으로 `Auto-Increment column`을 추가하고 `clustering key`로 선택. 

</aside>

- 장점
    
    > 읽기 작업이 주로일 때, 범위 조회나 정렬된 결과가 자주 필요할 때 사용!
    > 
    - 검색 속도가 빠르다.
        - leaf page에 데이터가 저장되어 있어서 추가적인 데이터 페이지 접근이 불필요
    - 데이터가 물리적으로 모여있어서
        - `BETWEEN`, `ORDER BY`, `GROUP BY`시에 압도적인 성능을 보임.
- 단점
    - 삽입 / 수정할 때마다 물리적 순서를 유지해야 하므로 → Page Split → 시스템 부하…

## Non-Clustered Index = Secondary Index

> 실제 데이터와 다른 무리의 인덱스 ex) `unique`
> 

<img width="559" height="413" alt="스크린샷 2026-02-20 오전 11 06 20" src="https://github.com/user-attachments/assets/6f0f1c6f-87e6-4a0e-9a85-818fb3b82aa3" />


- 원본 데이터베이스는 그대로 놔두고, 별도의 공간에 Index Page (= leaf page)을 생성!
    - like 책의 찾아보기
- 별도의 공간에 저장하므로 → 테이블당 여러 개를 만들 수 있다.
- `leaf page` → [`index key value` + `data address`] 을 저장.

- **장점**
    - `CUD` 성능이 유리
        - 물리적인 재배열이 일어나지 않으므로 Page Split이 덜 발생한다!
        - 인덱스를 상황에 따라 여러개를 생성할 수 있다.
- **단점**
    - 조회 속도가 느리다.
        - 인덱스 페이지에서 주소를 찾음 → 실제 데이터 페이지로 이동… 추가적인 단계가 필요
    - 저장공간이 추가로 필요 → 데이터 용량 증가!
    - Cluster Index의 PK가 변경되면, 이를 주소로 참조하는 모든 Non-Cluster index의 leaf page 정보도 갱신되어야 한다.

> 
> 
> - where 절 or join 절과 같이 조건문을 활용하여 테이블을 필터링할 때,
> - 데이터가 자주 업데이트 될 때,
> - 특정 컬럼이 쿼리에서 자주 사용될 때.
> 
> 사용된다!
> 

## Multi Column Index

https://dev.mysql.com/doc/refman/8.4/en/multiple-column-indexes.html

> 2개 이상의 column을 묶어서 만든 인덱스
> 
- 인덱스 생성 시에 설정한 컬럼 순서대로 정렬됨
    - `(col1, col2, col3)` 순서로 인덱스를 만들면, 데이터는 `col1`으로 먼저 정렬되고, `col1`이 같은 행들 사이에서만 `col2`가 정렬되며, 그 안에서 다시 `col3`가 정렬
- `mysql`의 경우에는 왼쪽부터 순서대로 조건절에 포함된 경우에만 인덱스를 활용해 검색을 수행할 수 있다.
    - **인덱스 활용이 가능한 경우 (col1, col2, col3 기준)**
        - `col1` 단독 조건
        - `col1` AND `col2` 조건
        - `col1` AND `col2` AND `col3` 조건
    - **인덱스 활용이 불가능한 경우**
        - `col2` 단독 조건 (왼쪽 끝인 col1이 빠짐)
        - `col2` AND `col3` 조건 (왼쪽 끝인 col1이 빠짐)
        - `col1` OR `col2` 조건 (OR 연산자는 인덱스 효율을 떨어뜨리거나 사용하지 못하게 함)

## Covering Index

> 쿼리를 실행하는 데 필요한 모든 컬럼 (`SELECT`, `WHERE`, `ORDER BY`, `GROUP BY`) 등이 인덱스에 이미 포함됨 → 실제 데이터 페이지를 조회하지 않아도 되는 상태!
> 

*HOW TO CHECK?*

실행 계획(`EXPLAIN`)을 확인했을 때, **`Extra` 컬럼에 `Using index`**라고 표시되면 커버링 인덱스가 적용된 것

⇒ 조회 속도가 매우 빠르고, 이미 정렬된 인덱스 구조를 활용하므로 `ORDER BY` or `GROUP BY` 시에 별도의 정렬 작업 없이 결과를 낼 수 있다!

## B+ tree

> B tree를 확장해서 데이터의 빠른 접근을 위한 인덱스 역할만 하는 비단말 노드를 추가한 트리!
> 

<img width="322" height="147" alt="스크린샷 2026-02-20 오전 11 06 44" src="https://github.com/user-attachments/assets/c810052e-ed7b-41a5-9b31-ea10f7c62477" />


- 오직 leaf node에만 데이터를 저장한다!
- 특징
    - Balanced Tree
        - root ~ leaf까지의 모든 경로 길이가 동일
        - 노드가 꽉 차면 split, 비면 merge or redistribution을 통해 균형 유지!
    - 노드 구성 원칙 (Fan - out)
        - 중간 노드는 $\lceil n/2 \rceil$ ~ $n$ 개의 자식을 가짐.
        - leaf node는 키 값들이 오름차순으로 정렬되어 있다.
- 연산 메커니즘
    - Insertion
        - leaf node에 빈자리가 있으면 정렬 상태를 유지하면서 삽입함.
        - `Overflow`
            - 노드를 반으로 분할 → 중간 키 값을 parent node로 올린다.
    - Deletion
        - leaf node에서 값을 제거한다.
        - `Underfull`
            - `redistribution` : 인접한 형제 노드에서 키를 빌려옴.
            - `merge` : 형제 노드랑 합친다.

> `B-tree` 보다는 `B+tree`를 선호한다.

***WHY?***
Range Query의 효율성과 메모리 활용도때문에.

1. `B+tree`는 리프 노드들이 linked list로 이어져 있어서 특정 범위의 데이터를 빠르게 스캔할 수 있다.
2. `B+tree`는 중간 노드에 실제 데이터가 없다 → 한 노드에 많은 인덱스 정보를 담을 수 있다!
> 

<aside>
💡

| **구분** | **B-Tree** | **B+Tree (주로 DB 인덱스로 사용)** |
| --- | --- | --- |
| **데이터 저장** | **모든 노드**(루트, 중간, 리프)에 데이터 저장 | **오직 리프 노드**에만 데이터 저장 |
| **중간 노드 역할** | 데이터 저장 + 가이드 역할 | **가이드 역할**만 수행 (Index Set) |
| **리프 노드 연결** | 연결 없음 | **Linked List**로 서로 연결됨 |
| **탐색 성능** | 운 좋으면 루트에서 끝남 (가변적) | 항상 리프까지 내려감 (균일함) |
| **범위 검색** | 모든 노드를 순회해야 해서 불리함 | 리프만 따라가면 되어 **매우 유리**함 |
</aside>

## Scan

https://wvwv.tistory.com/115

### Table Full Scan

> 테이블에 속한 모든 레코드들을 처음부터 끝까지 읽는다.
> 
- **동작 원리**: 인덱스를 거치지 않고 데이터 파일의 모든 블록을 순차적으로 읽어 메모리에 올린다.
- **Use Case**
    - **1.** `SUM`, `AVG`, `COUNT` 등 **집계 함수**를 사용하여 테이블 전체 데이터가 필요한 경우.
    - **2.** 조회하려는 데이터가 테이블의 상당히 높은 비중(`High Selectivity`)을 차지할 때.
    - **3.** 테이블의 크기가 아주 작아 인덱스를 타는 것보다 한 번에 다 읽는 게 빠를 때.
    - **4.** 적절한 인덱스가 존재하지 않을 때.
- **특징**
    - 대량의 디스크 I/O를 유발하므로, 일부 데이터만 찾는 쿼리에서 발생하면 **성능 저하의 주원인**이 된다.

### Index Range Scan

> 인덱스를 사용해서 특정 범위의 데이터만 골라낸다.
> 
- **동작 원리**: `B-Tree` 구조의 루트 노드에서 브랜치를 거쳐 리프 노드에 도달한 뒤, 필요한 **범위(`Range`)만큼 수평적으로 스캔.**
- **Use Case**
    - `BETWEEN`, `<`, `>`, `>=`, `<=` 등의 **범위 조건**이나 `LIKE 'A%'`와 같은 전방 일치 조건을 사용할 때.
    - **인덱스 선두 컬럼**이 조건절에 가공되지 않은 상태로 포함되어야 합니다.
- **특징**:
    - 인덱스는 정렬되어 있으므로 별도의 **Sort 연산을 생략**할 수 있다.
    - 스캔을 통해 얻은 `Rowid`를 바탕으로 테이블에 접근하므로, 읽어야 할 범위가 너무 넓으면 성능이 오히려 저하될 수 있다.

### Index Full Scan

> 인덱스 페이지 전체를 처음부터 끝까지 스캔한다.
> 
- **동작 원리**: 수직적 탐색(루트->리프) 없이 리프 블록의 `Double Linked List`를 따라 처음부터 끝까지 읽습니다.
- **Use Case**
    - `WHERE`절 조건이 없더라도, 쿼리에 사용된 컬럼이 모두 인덱스에 포함되어 있을 때 (커버링 인덱스와 유사).
    - 결과를 인덱스 키 순서대로 정렬해서 보여줘야 하는데, 테이블 전체 스캔 후 정렬하는 것보다 인덱스를 다 읽는 게 더 빠를 때.
- **특징**:
    - 인덱스의 크기는 보통 테이블보다 훨씬 작기 때문에, `Table Full Scan`보다 I/O 부하가 적다.
    - 단, 인덱스에 없는 컬럼을 조회해야 한다면 레코드마다 테이블에 접근해야 하므로 옵티마이저는 이 방식을 선택하지 않을 확률이 높다.

`anamoly`의 종류

1. **Insertion Anamoly**
삽입할 때 → 원하지 않은 값들도 함께 삽입됨.
2. **Deletion Anamoly**
한 tuple을 삭제할 때, 원하지 않는 값들도 함께 삭제됨.
3. **Update Anamoly**
튜플들의 속성 값을 갱신할 때, 일부 튜플의 정보만 갱신됨.

### BCNF

| 학생 | 과목 | 교수 | 학점 |
| --- | --- | --- | --- |
| 1 | AB123 | 김인영 | A |
| 2 | CS123 | Mr.Sim | A |
| 3 | CS123 | Mr.Sim | A |

위에서는 후보키가 아닌 교수가 과목을 결정하기 때문에, 과목을 중심으로 아래와 같이 쪼개야 한다.

| 교수 | 과목 |
| --- | --- |
| 김인영 | AB123 |
| Mr.Sim | CS123 |

| 학생 | 과목 | 학점 |
| --- | --- | --- |
| 1 | AB123 | A |
| 2 | CS123 | A |
| 3 | CS123 | A |

**결정자 = 후보키**

즉, 어떤 속성을 결정하는 사람은 반드시 candidate key여야 한다!

ex) 교수는 한 과목만 강의한다면, {교수, 과목}, {학생, 교수}로 테이블을 분리!

> **Prob :** 하지만 위와 같은 정규화 과정은 Relation의 분리로 인해서 Relation 간의 연산이 많아져서 질의에 대한 응답 시간이 느려지게 됨!

# De-normalization

> **Sol :** 데이터의 성능 향상을 위해, 데이터 중복을 허용 & JOIN을 줄여서 → DB의 성능을 향상시킨다!

정규화 & 반정규화는 `Trade off` 관계에 있음
> 

즉, 데이터무결성을 보장하지는 않지만 성능은 향상됨. 

어떤 성능? Read 성능, but CUD 성능은 낮아짐.

***그럼 어떤 경우에 사용할까?***

- 정규화를 수행했지만 수행속도가 느려진 경우
- 다량의 범위를 자주 처리해야하는 경우
- 특정 범위의 데이터만 자주 처리하는 경우
- 요약/집계 정보가 자주 요구되는 경우

# Connection Pool

> `Application` & `Database Server`가 통신할 수 있도록 하게 하는 기능!
> 

```java
public Connection getConnection() {

        try {
            return DriverManager.getConnection("jdbc:mysql://" + SERVER + "/" + DATABASE + OPTION, USERNAME, PASSWORD);
        } catch (final SQLException e) {
            System.err.println("DB 연결 오류:" + e.getMessage());
            e.printStackTrace();
            return null;
        }
    }
```

데이터베이스와의 연결 객체를 미리 생성 

→ `Pool` (보관소) 에 저장해두고 

→ 필요할 때마다 빌려주고 반납받는 `Caching` 매커니즘!

이로써 DB 연결을 매번 새로 생성 할때의 cost를 줄여준다.

> DB 연결 할 때 cost
1. network overhead - TCP / IP 연결 및 인증 과정에서 시간 소모
2. resrouce 낭비 - 객체 생성은 CPu & 메모리 자원을 크게 소모!
3. 서버 부하 - DB 서버가 감당할 수 있는 동시 세션 수에 제한있음 → 서버 장애로 이어질 수 있다.
> 

- 동작원리
- 
    
    <img width="540" height="283" alt="스크린샷 2026-02-20 오전 11 08 22" src="https://github.com/user-attachments/assets/5058f601-2ea6-4987-93a9-86418040ba88" />

    - **애플리케이션 시작**: 설정된 크기만큼 `Connection` 객체를 미리 생성하여 `Pool`에 담는다.
    - **요청 발생**: 사용자가 DB 작업이 필요하면 Pool에서 노는(Idle) 커넥션을 빌려온다.
    - **작업 수행**: 빌려온 커넥션으로 SQL을 실행한다.
    - **반납**: 작업이 끝나면 `close()`를 호출하여 연결을 끊는 대신 **Pool에 다시 반납한**다.
- 장점
    - **성능 향상** : 미리 연결된 객체를 재사용하여 응답 시간 단축
    - **자원 효율성** : 정해진 수의 커넥션만 유지하여 서버 과부하 방지
    - **동시성 관리** : 다수의 요청이 들어와도 안정적으로 처리 가능
- 단점
    - **메모리 소비** : 일정 수의 연결을 항상 유지하므로 리소스를 점유함
    - **커넥션 누수** : 제대로 반납(`close`)하지 않으면 사용할 수 있는 커넥션이 고갈됨
